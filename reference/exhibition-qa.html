SentinelGUI — Exhibition Q&A

Anticipated questions from judges and visitors · July 2026

One-liner pitch: “We built an open-source SCADA dashboard for industrial process monitoring that costs nothing, runs on any laptop, and explains faults in plain language — no expensive PLCs or proprietary software required.”

Project Motivation

Q: Why did you build this? Why not use existing SCADA software?

Short answer: Commercial SCADA (Siemens WinCC, Aveva, Ignition) costs thousands of dollars per license, requires industrial PLC hardware, and is a black box — you cannot read the source code or modify it.

Long answer: We wanted an educational tool where students can:

  1. See every line of code that processes a sensor reading
  2. Understand why a fault is diagnosed (the rule engine is readable Python, not a hidden algorithm)
  3. Add new sensors, faults, or scenarios by editing JSON config files — no recompilation
  4. Run the entire system on a $30 Arduino and a laptop, no industrial hardware required

This makes it ideal for chemical technology education, where the focus should be on understanding the process — not on fighting proprietary configuration tools.

Q: How is SentinelGUI different from other open-source SCADA tools (ScadaBR, OpenSCADA)?

Existing open-source SCADA tools are still heavy — they require a web server, database, and often Java runtime. SentinelGUI is intentionally minimal:

  • One command to run: python -m sentinelgui --simulate
  • Zero configuration files for basic use — sensible defaults built in
  • Rule-based diagnosis is built-in, not an afterthought. The fault engine (fault_engine.py) is 200 lines of pure Python — you can read it in 10 minutes
  • Multi-scenario: switch from reactor cooling to distillation column to contact process by changing one CLI flag. In commercial SCADA, this requires redesigning the HMI screens
  • No database: state lives in memory (rolling window). For a teaching lab, persistent storage is overhead without benefit
Q: Who is this for?
Chemical technology students and educators. It demonstrates how real-time monitoring, alarm management, and fault diagnosis work in industry — without the cost and complexity of an actual plant. It also serves as a project reference for Python learners who want to see how threading, queues, GUIs, and serial communication fit together in one application.

Architecture & Design

Q: Walk me through the data flow — from sensor to screen.
  1. Data source: Either an Arduino sending CSV frames over USB serial (acquisition.py) or the built-in FaultSimulator (simulator.py). Both push raw dicts onto a queue.Queue.
  2. Process engine (process_engine.py): The UI thread pops from the queue, converts raw values to engineering units, and creates a Reading object.
  3. Reading window (reading_window.py): A bounded deque that stores the last 300 readings for trend calculations.
  4. Alarm manager (alarm_manager.py): Classifies each sensor into normal / warning / critical using two-band thresholds. Applies debounce to prevent flickering.
  5. ReAct agent (react_agent.py): Calls fault_engine.classify() to produce a diagnosis. Generates a human-readable trace (Observe → Reason → Act).
  6. Dashboard: Updates sensor cards, trend charts, mimic diagram colours, alarm panel, and trace panel based on the AgentResult.
Q: Why does the UI never freeze? How does threading work?

The critical insight is that tkinter is not thread-safe — all UI updates must happen on the main thread. The architecture works around this:

  • Background thread (serial reader or simulator) blocks on I/O and pushes raw frames onto a queue.Queue
  • Main thread runs a poll() timer every 100ms that drains the queue and processes readings
  • The queue acts as the thread-safe rendezvous point — the background producer never touches UI objects

This is a classic producer-consumer pattern. The UI stays responsive because the main thread never blocks on I/O.

Q: What happens if the Arduino disconnects mid-operation?
After 2 missed readings (2 seconds of silence), the controller automatically falls back to the built-in simulator. The user sees a status bar message: “Serial link lost — auto-recovering into simulation mode”. The demo continues without interruption. This is handled in app.py _auto_recover_to_simulator().

Fault Diagnosis

Q: How does the fault diagnosis work without AI?

fault_engine.py implements a rule-based classifier. For each reading, it checks against 6 fault signatures in order of specificity:

  1. Pump failure — flow near zero AND pressure low
  2. Blockage — flow low AND pressure high
  3. Cavitation — pressure low AND oscillating
  4. Thermal runaway — temperature above critical limit
  5. Cooling failure — temperature elevated despite adequate flow
  6. Fouling — temperature elevated AND flow mildly reduced
  7. Undetermined — no signature matched

The first match wins. This deterministic approach means the same input always produces the same diagnosis — no training data, no API call, no randomness.

Q: How do you tune the thresholds for different processes?
Each scenario (reactor, boiler, distillation, contact process) has its own JSON config file under config/scenarios/. The fault_tuning block contains process-specific constants like temp_warn, flow_near_zero, press_low. The set_tuning() function in fault_engine.py applies these on scenario switch — no code changes needed. For example, a steam boiler operates at 180°C, while a contact process converter runs at 430°C; the thresholds adjust accordingly.
Q: When would you use the optional AI diagnosis?
The rule-based engine handles the 6 fault signatures we designed for. But if an unexpected pattern appears (noise, sensor drift, novel fault), the AI enrichment button sends the alarm context to Google Gemini for a natural-language explanation. The rule engine still runs first — AI is advisory, not primary. This is implemented in sentinelcli_bridge.py using the Gemini REST API over urllib, with a 10-second timeout so it never blocks the UI.

Multi-Scenario System

Q: What processes does SentinelGUI support?
Four scenarios, switchable via --scenario flag:
  • Reactor cooling loop (default) — jacket-cooled batch reactor, 0–100°C
  • Steam boiler — high-pressure steam generation, 100–250°C
  • Distillation column — binary distillation with reboiler and condenser, 40–120°C
  • Contact process — sulfuric acid production (SO₂ → SO₃), converter bed at 430°C
Each has custom sensor labels, thresholds, stage names, fault targets, and chemistry explanations — all in JSON, no code changes.
Q: How does the mimic diagram adapt to different processes?
The MimicDiagram widget reads the stages array from the scenario JSON. For the reactor: Reservoir → Pump → Flow Sensor → Pressure Sensor → Reactor → Reservoir. For the contact process: Sulfur Burner → Blower → Flow Sensor → ΔP Sensor → Converter. The widget draws one rectangle per stage, connects them with arrows, and colours each stage based on its sensor zone or the active fault type — all dynamically, no hardcoded layouts.

Exhibition & Practical Concerns

Q: What if the demo laptop doesn't have an Arduino?
Use --simulate flag. The built-in FaultSimulator generates realistic readings at 1 Hz with adjustable noise and fault injection. You can demonstrate every feature without any hardware. The simulator also auto-activates if the serial port fails to open.
Q: What about the physical model on display?
The thermocol (styrofoam) model represents the contact process flow path: sulfur burner → converter → absorption tower. It is a non-functional visual aid — the actual monitoring and fault diagnosis happens in the SentinelGUI software running on the laptop beside it. The model helps visitors understand the process layout while the software demonstrates the monitoring and control logic.
Q: How portable is SentinelGUI?
Pure Python 3.14+. Runs on Windows, Linux, and macOS. The only dependencies are pip-installable. No Docker, no VM, no web server required. A student can clone the repo and be running in under 2 minutes.
Q: What came next? Future features?
  • Data logging to CSV for post-exercise analysis
  • Custom scenario builder UI (instead of hand-editing JSON)
  • OPC-UA bridge for connecting to real industrial PLCs
  • Historical trend playback (rewind and replay past sessions)
Remember: Judges care about “why” more than “what.” For every feature, you should be able to say “we did it this way because…” If you get stuck, say “that's a great question — let me show you in the code.” Opening the actual file and pointing to the line is more impressive than memorising an answer.
