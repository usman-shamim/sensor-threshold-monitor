Lesson 1: The Repo Map

📁 SentinelGUI codebase ⏱ ~10 min 🎯 See the whole picture before any detail

You generated a real working codebase. Before diving into any single file, you need a mental map — where things live, what each piece is responsible for, and how data flows from the Arduino to your screen. That's this lesson.

Two projects, one repo

Your repo contains two separate tools that cooperate:

  sensor-threshold-monitor/
  │
  ├── project.py          ← SentinelCLI  (CS50P project — DO NOT MODIFY)
  ├── test_project.py     ← SentinelCLI tests
  ├── config.json         ← SentinelCLI thresholds
  │
  └── sentinelgui/        ← SentinelGUI  (everything you're learning)
      ├── __main__.py       entry point  →  python -m sentinelgui
      ├── app.py            controller
      ├── models.py         data shapes
      ├── ...               (9 more logic modules)
      └── dashboard/        all GUI widgets
Golden rule: SentinelGUI imports project.py for its threshold logic. It never modifies it. The CLI and the GUI are independent — each works without the other.

The 12 modules — one job each

Inside sentinelgui/ there are 12 headless (no GUI) logic modules and 8 dashboard widgets. Each module has exactly one job. This is the most important design principle in the whole codebase.

File One job
models.py Define data shapes — Reading, Alarm, FaultDiagnosis
reading_window.py Keep the last 300 readings in memory; compute slopes
acquisition.py Read serial frames from the Arduino on a background thread
simulator.py Fake the Arduino when no hardware is connected
process_engine.py Convert raw numbers into engineering units (°C, bar, L/min)
thresholds.py Decide if a reading is normal / warning / critical
alarm_manager.py Raise and clear alarms; keep alarm history
fault_engine.py Name the fault — blockage? pump failure? cavitation?
react_agent.py Observe → Reason → Act loop that ties everything together
sentinelcli_bridge.py Call the Gemini AI for richer explanations (optional)
data_logger.py Write readings to a CSV file
shutdown_controller.py Trigger emergency shutdown and latch the safe state
app.py The conductor — owns the queue, drives all the above each tick

How data flows — one reading's journey

Every second, one sensor reading travels through the entire system:

Arduino (or Simulator)
        │   "72.4,34.1,3.2\n"       raw CSV text over USB
        ▼
  acquisition.py  ──────────────────  parse_frame()  →  raw tuple
        │
        ▼
  queue.Queue  ◄──────────────────── background thread pushes here
        │
        ▼
  app.py  drain()  ◄──────────────── Tk calls this every 250 ms
        │
        ├──▶  process_engine.py  →  Reading(temp=72.4, flow=34.1, pressure=3.2)
        │
        ├──▶  thresholds.py      →  zones = {temp:"normal", flow:"warning", pressure:"normal"}
        │
        ├──▶  reading_window.py  →  add to rolling buffer (last 300 readings)
        │
        ├──▶  react_agent.step() →  AlarmManager + fault_engine + diagnosis
        │
        └──▶  MainWindow.update()  →  renders cards, charts, mimic, alarms, diagnosis

Why is this good design?

Each module can be tested in isolation — you can import fault_engine.py and feed it fake readings without opening a window or connecting hardware. That's why pytest sentinelgui/tests/ runs in under 1 second with no USB cable.

It also means you can swap pieces. Want a different fault classifier? Replace fault_engine.py. Want to log to a database instead of CSV? Replace data_logger.py. Nothing else needs to change.

Key idea: Separate what you know (logic modules) from what you show (dashboard widgets). Logic modules import nothing from dashboard/. Widgets only render — they contain zero business logic.
