Lesson 1: Exhibition Walkthrough

Explain SentinelGUI to judges in 5 minutes · Dependencies ref · Q&A ref

Goal: Walk a judge through the system so they understand what it does, how it works, and why it matters — all in 5 minutes. Use this script as a spine; adapt based on what the judge asks about.

Phase 1: The Pitch (30 seconds)

Say this:
“This is SentinelGUI — an open-source SCADA dashboard for monitoring industrial chemical processes. It reads temperature, pressure, and flow sensors, detects faults in real time, and explains the likely cause in plain language. It runs on any laptop with Python, costs nothing, and you can read every line of code.”

See Dependencies Reference for the comparison table vs. commercial SCADA. See Exhibition Q&A for the “Why not use Siemens WinCC?” answer.

Phase 2: Live Demo (2 minutes)

Step 1 — Start the app

Open a terminal and run:

python -m sentinelgui --simulate --kiosk --scenario contact

Explain: --simulate means no Arduino needed, --kiosk is exhibition mode (fullscreen, large text), --scenario contact selects the sulfuric acid contact process.

Step 2 — The dashboard

Point to each area:

  1. Sensor cards (top) — show live values coloured by zone: green = normal, amber = warning, red = critical
  2. Trend charts — rolling graph of the last 60 readings per sensor
  3. Mimic diagram — process flow diagram showing Sulfur Burner → Blower → ΔP Sensor → Converter, coloured by health
  4. Alarm panel — history of alarms with severity and timestamp
  5. Trace panel — the agent's reasoning in Observe → Reason → Act format

Step 3 — Inject a fault

Click the Inject Fault button and choose “Blockage”.

What happens:

  • Flow rate drops (blockage restricts flow), pressure rises (fluid backs up)
  • Sensor cards turn red
  • Mimic diagram stages change colour
  • Alarm panel shows a new critical alarm
  • Trace panel prints: “Observe: flow 2.1 → critical, press 4.5 → critical. Reason: blockage (high confidence). Act: raised critical alarm 'Flow Sensor'”

Key point to make: “The diagnosis came from a rule engine in 200 lines of Python — no AI, no cloud, no training data. We can trace exactly why it decided ‘blockage’ and not ‘pump failure’.”

Step 4 — Clear and switch scenarios

Click Clear Fault → values return to normal. Then switch scenario from the dropdown to “Steam Boiler”.

Explain: “The entire dashboard reconfigures — new sensor labels, new thresholds, new mimic stages. All from one JSON file. In commercial SCADA, this would take hours of HMI re-engineering.”

Phase 3: Architecture Deep-Dive (1 minute)

If a judge asks how it works internally, show this map:

   Arduino                            Python
   ───────                            ──────
   USB serial                      acquisition.py (pyserial)
       │                                  │
       │                          queue.Queue (thread-safe)
       │                                  │
       │  ┌───────────────────────────────┘
       │  ▼
       │  process_engine.py  →  Reading object
       │      │
       │      ├── reading_window.py  (last 300 readings)
       │      ├── alarm_manager.py   (zone classification + debounce)
       │      ├── fault_engine.py    (rule-based classifier, 6 faults)
       │      └── react_agent.py     (Observe → Reason → Act)
       │              │
       │              ▼
       │      dashboard/ (customtkinter + matplotlib)
       │      sensor_cards, trend_charts, mimic_diagram,
       │      alarm_panel, trace_panel, fault_log

Each file is listed in Dependencies Reference.
